# 設計メモ: テスト基盤の方針

[← README に戻る](../../README.md)

> **この文書の位置づけ**: これは laarma の**確定した設計方針**を記録する設計メモである。
> 「テストをどの基盤でどう書くか」という設計判断の正典。利用ガイド（どう実行するか）は
> [BENCHMARK.md](../BENCHMARK.md) にあり、本メモはそれとは別に「なぜこの基盤を選ぶか／
> いつ別の基盤を導入するか」という判断を記録する。

## 方針（要約）

laarma のテストは2層に分けて考える。

1. **回帰・シナリオテスト** → `my_project/benchmark.py` のシナリオ追加で行う。新たに pytest 等のテストファイルは作らない。
2. **クラス・関数レベルの単体テスト（pytest 等）** → 現時点では導入しない。ただし将来的な導入の余地は残す（判断基準は後述）。

## 1. 回帰・シナリオテストは benchmark.py で行う

**何をするか**: 新しい回帰ケースは、`my_project/benchmark_data.jsonl` にケースを追加し、`benchmark.py` を実行して検証する。LLM 判断が必須なケースには `pipeline_only: true` を付ける。

**なぜ benchmark.py か**:

- laarma の回帰検証は「ある (user_intent, action, environment) に対して期待する decision が出るか」という形をしている。これは benchmark_data.jsonl のケース追加 + benchmark.py の実行で自然に表現できる。
- 意図整合性の検証は LLM 呼び出しを伴う。`benchmark.py` は `--mode`（`pipeline` / `policy-engine` / `intent-alignment`）でモード分けされており、LLM を要するケースと要さないケースを切り分けられる。純粋な単体テストの枠組みより、この既存のモード分けに乗せる方が、laarma の評価構造と整合する。
- 別のテスト基盤（pytest 等）を並立させると、検証ロジックが2か所に分散し二重管理になる。プロトタイプ段階では基盤を1つに保つ方が、保守コストが低い。

**`pipeline_only` の扱い**: policy-engine モードはスタブ IntentAlignment（常に ALLOW）を注入するため、IntentAlignment による上書き（意図外 → DENY）は検証できない。意図整合性が肝のケースは `pipeline_only: true` を付け、LLM を呼ぶ pipeline モードでのみ実行する。これらのケースは API キーのある環境でしか回らない点に留意する。

## 2. クラス・関数レベルの単体テストは現時点では導入しない

**判断**: pytest 等によるクラス・関数レベルの単体テスト、カバレッジ計測、リファクタリング用テストハーネスは、**現時点では導入しない**。

**理由（コストとメリットの天秤）**:

- 現状はプロトタイプ段階であり、AARM 仕様の精査が完了していない。`PolicyEngine` の提案/上書きモデルへの作り変えのような大規模リファクタリングが、今後も随所に発生しうる（今回のリファクタリングはあくまで一例）。
- この段階でクラス・関数レベルの単体テストを実装すると、ソース変更のたびにテスト改修コストが乗り、変更を重くする。仕様精査に伴う設計変更が続く間は、このコストがデグレ防止のメリットを上回る。
- 単体テストが正当化されるのは、**コードが安定し、かつ本番リリース後のデグレによる不具合を絶対に避けたいという要件が出てきた段階**である。そうなって初めて、テスト改修コストを払う価値が、デグレ防止の確実性に見合う（導入はその要件を視野に入れた段階で行うことになり、必ずしも本番リリース後とは限らない）。

**将来導入する場合の方針**:

- 導入が正当化される段階になったら、SDK 内部の**純粋ロジック**（LLM 非依存の部分）から pytest を導入するのが妥当。具体的には、収束ループ、`_match_conditions`、変換レジストリなど、入力に対して決定的な出力を返す関数。これらは LLM を要さないので単体テストと相性が良く、回帰の費用対効果が高い。
- 意図整合性を含む end-to-end の検証は、引き続き benchmark.py（LLM を呼ぶ pipeline モード）で行う。単体テストはこれを置き換えるものではなく、純粋ロジックに対して補完的に追加するもの。

**手続き上の約束**: 新しいテストフレームワークを導入したくなったら、**実装に入る前に相談する**こと。プロトタイプ段階でテスト基盤を分散させない、という上記の判断を、その時点で見直すべきかどうかを確認してから動く。
